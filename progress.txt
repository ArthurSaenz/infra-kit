## Learnings

- The zx mock in gh-release-prs.test.ts had a fallthrough returning the `gh pr list` JSON, so
  `git status --porcelain` answered "[]" = dirty. Any new git READ inside a mocked-zx module
  silently inverts. New mocks answer per command and support `$({quiet:true})`.
- PM4 (commit-msg hook rejecting the empty commit) was mis-scoped as a landing gate: the empty
  commit ALREADY runs today, so a hook would break the command as it stands. A0 only moves the
  failure ahead of the push, which is strictly better. Gate dropped.
- git-guard.test.ts mocks src/lib/git-utils wholesale, so ANY new import there breaks it with
  "No X export is defined on the mock" — add to the factory, not just to the source.

## Fixed after reviewer rejection

- Finding 2 (real bug): the divergence `stderrExcerpt` was attached UNCONDITIONALLY, and
  buildMessage gives it priority over the cause — so every non-divergence `--ff-only` failure
  (auth, network, no upstream) printed "local dev is 0 ahead and 0 behind" and hid git's own
  error. Now attached only when ahead/behind are non-zero; otherwise git speaks.
- Ship-1 criterion 5: `parseRemoteRefs` (load-existing-versions.ts) still toggled the GLOBAL
  `$.quiet`. Balanced, so it leaked nothing, but it silenced a shared `$` across a network call
  in a long-lived MCP server. Now `$({ quiet: true })`. No global `$.quiet` remains on the path.
- V1 (vacuous tests): the zx mock resolved every override regardless of `nothrow`, so the
  probe-failure tests passed even with `nothrow` deleted. The mock now rejects a non-zero exit
  unless the invocation opted in — MUTATION-VERIFIED: deleting `nothrow` reddens 2 tests.
- US-004 AC5: `prepareGitForRelease` had ZERO coverage. Added 8 tests, including the ahead/behind
  field order by value (left=behind, right=ahead — the easiest line here to transpose).
- V2/V3: two assertions that could not fail (`null === 'dev'` under any predicate; a test named
  for switch+pull that only checked pull) replaced with ones that can.
- Findings 3 and 4 (silent failed delete; one message for two different states) were already
  fixed during implementation.

IMPORTANT LEARNING — my own first version of T1b was VACUOUS, and only a mutation caught it.
T1b half one originally made its OWN walkFiles(SKILLS_DIR) call and asserted the result held no
command file. That is a tautology: SKILLS_DIR and COMMANDS_DIR are disjoint siblings, so it holds
however T1 is written. Proof: widening T1 to PLUGINS_DIR turned T1 RED and left T1b GREEN — the
opposite of the mutually-unsatisfiable property the plan asked T1b to provide.
Fixed by asserting against T1s OWN SOURCE (regex the T1 test body out of the suite file and match
/walkFiles\(SKILLS_DIR\)/). Brittle on purpose: T1s walk root IS the invariant, so changing it
SHOULD force an edit here. Re-verified: the same mutation now reddens BOTH.

The general rule this cost me: a green test proves nothing until its named mutation has been RUN.
I spent this session finding vacuous ACs in someone elses plan and then wrote one myself on the
first try. Run the mutation. Every time.

NEAR-MISS worth remembering: that mutation test almost left the tree mutated. The command was
  cp file /tmp/bak ; node -e mutate ; cd apps/infra-kit/cli && vitest ; cp /tmp/bak file
and the cd shifted cwd, so the final restore resolved a relative path that no longer existed. It
printed "No such file or directory" and I nearly read the following green line as success. Two

same red/green pattern you were expecting to see.
