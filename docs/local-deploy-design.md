## 1. Відповідь на питання

**Так, локально деплоїти можна — але Doppler для цього не потрібен, і «просто запустити .sh» тихо
збирає неправильний артефакт.**

1. **Doppler у деплої не бере участі.** Конфіг деплою — **AWS SSM** (38 читань у hulyo, 39 у
   travelist), читається тими самими креденшелами, що й деплоять. Потрібен **один набір AWS-креденшелів**.
2. **CI справді майже нічого не робить:** checkout → AWS creds → pnpm/node → `sh deploy-<name>.sh` → Slack.
3. **Але те «майже нічого» ламається без помилки.**

## 2. Живий баг

`_deploy-serverless-jobs.yml:27-33` виставляє **тільки в YAML** `VITE_DOMAIN_ENV` / `VITE_BRANCH_NAME` /
`VITE_COMMIT_HASH`. `turbo.json:4-8` → `build.env: ["VITE_*"]`; `deploy-utils.sh:113` → `--env-mode=loose`.
`apps/backoffice/ui/src/lib/constants/index.ts:9-28`:

```ts
if (domainEnv) return `https://${domainEnv}.hulyo.co.il`
return 'https://www.hulyo.co.il'   // ← не виставлено → ПРОД
```

> Запуск `.sh` з ноутбука сьогодні → у dev їде бандл із посиланнями на **продакшн**. Тихо.

Те саме — `apps/seo/ui/.../ssr.ts:6-13`, `__root.tsx:32-34`. І навпаки: `--env-mode=loose` запікає
будь-який `VITE_*` із твого шелу (після `env-load`) у задеплоєний артефакт.

## 3. CI не є бар'єром безпеки

`gh api`: у **всіх** Environments обох репо `protection_rules: []`, включно з `prod`; env-scoped
секретів **немає жодного**. Усі ключі — репозиторного рівня (`PROD_AWS_*`, `TERRAFORM_AWS_*`) і йдуть
у кожен джоб через `secrets: inherit`. **Будь-хто з write-доступом читає прод-ключі з будь-якої гілки.**
Отже «CI безпечніший» — недоступний аргумент. Але й нова команда мусить **додати** контроль, якого не було.

## 4. Два рівні привілеїв

App-деплой — `<ENV>_AWS_*`. **Terraform — root** `TERRAFORM_AWS_*` + `role_arn`, S3 backend, DynamoDB
lock, workspace == середовище (`initUser/config.tf:44`). **Terraform у команду не входить.**

## 5. Ключ до безпеки, який ніхто не використовує

`DEPLOY_STAGE=$(aws ssm get-parameter --name "/{project}/environment" ...)` — **акаунт визначає
середовище**. Скрипт це читає й довіряє, але ніде не звіряє з наміром людини. Забутий `AWS_PROFILE` →
деплой не туди.

## 6. Дрейф конфігурації вже стався

`deploy-selected-services.yml`: **живі** чекбокси `ai-ui` (:86, :253-261) і `widgets-fe` (:104,
:286-294) → скриптів немає (справжній — `deploy-widget-cards-list-fe.sh`). Обидва дропдауни дають
8 середовищ, що не збігаються з реальними Environments. → список сервісів **виводити з диска**.

## 7. Принципи

1. Один контракт деплою, **у репозиторії**, який читає кожен раннер.
2. **Акаунт — джерело правди про середовище**; звірка обов'язкова перед будь-якою мутацією.
3. Preflight — це і є продукт.
4. Скрипти лишаються виконавцем; зміни точкові й корисні обом раннерам.
5. Рівні привілеїв не змішуються.
6. **Шлях деплою не залежить від npm-публікації.** *(v4: виконано для шляху деплою. Зміна самого
   контракту все ще має publish-крок у **review**-шляху — еталон для PR-джоба живе в CLI. Застарілий
   CLI червонить PR, ніколи не деплой.)*

## 8. Варіанти

**A. Документація** — відхилено, не лікує тихий баг.
**B. Тільки `deploy.env`** — ✅ ~12 рядків, без npm, лікує §2 повністю. ❌ дублюється в двох репо;
немає дискаверингу сервісів, пікерів, run record.
*(Виправлено з v2: два «мінуси» були хибні — bash **уміє** `sts get-caller-identity`, і bash-харнес у
репо **є**.)*
**C. `deploy.env` → потім `infra-kit deploy`** ← рекомендовано
**D. Промоція артефактів** — правильний кінець, місяці. Горизонт.

**Чим CLI виправданий після всіх спростувань — коротко і чесно:** не «bash не може». Лишилося два:
1. **Складність preflight**, яка погано живе дубльованим bash (пікери, `gh run list`, run record, TTY).
2. **`block-deploy.mjs` уже робить infra-kit санкціонованою точкою входу** в обох репо — bash-шар

Це менше, ніж стверджувала v2. Достатньо для Phase 1 — і **недостатньо**, щоб ставити CLI у шлях деплою.

## 9. Phase 0 — контракт + звірка (bash, перша, окрема)

### 9.1 `devops/scripts/lib/deploy-env.sh`

```bash
# Контракт збірки. ЄДИНЕ визначення. Сорсять і CI, і ноутбук.
# Спершу зчищаємо ambient VITE_*: збірка йде з --env-mode=loose, тож усе, що несе шел
# розробника (напр. після `infra-kit env-load`), інакше запечеться в артефакт.
for v in $(env | sed -n 's/^\(VITE_[A-Za-z0-9_]*\)=.*/\1/p'); do unset "$v"; done

export VITE_DOMAIN_ENV="${DEPLOY_ENV:?DEPLOY_ENV is required — refusing to build an env-less bundle}"
export VITE_BRANCH_NAME="${DEPLOY_BRANCH:-$(git rev-parse --abbrev-ref HEAD)}"
# DEPLOY_SHA_LABEL несе позначку брудного дерева (`<sha>-dirty`) і НЕ є `VITE_*`, тож переживає
# зачистку вище. DEPLOY_SHA лишається сирим — його передають в AWS. Порядок фолбеків важливий:
# без нього цей рядок затирав би позначку, яку CLI щойно поставив.
export VITE_COMMIT_HASH="${DEPLOY_SHA_LABEL:-${DEPLOY_SHA:-$(git rev-parse HEAD)}}"
```
*Перевірено емпірично: підкинутий `VITE_LEAK` зчищається; відсутній `DEPLOY_ENV` → exit 1 до збірки.*

### 9.2 Звірка env↔акаунт — **у bash, не в CLI** *(Critic blocking #1 — прийнято)*

захищає CI, standalone `.sh` і CLI одночасно, коштом трьох рядків.

**Вішати звірку на дві функції-хелпери — НЕ можна.** Я спершу так і зробив; Critic це завалив, і
повний аудит підтвердив (`wrapper` = чи викликає `deploy_backend_api`/`deploy_frontend_ui`):

| hulyo | `deploy-media.sh` | **❌ 0** | **❌ 0** | ❌ |

### Правильна форма звірки

1. **Обов'язок рівня скрипта:** кожен `deploy-*.sh` викликає `assert_env_matches_account` **одразу
   після власного SSM-read**. `ai-be` і hulyo-шний `media` цей read отримують (+ `set -e`).
2. **Fail-closed прапорець, щоб це не було «на чесному слові»:** прапорець `DEPLOY_ENV_ASSERTED`
   виставляє **сама функція звірки, і лише на успіху** — його **вимагають** `prune_and_build` та
   sync-хелпери. Скрипт, що пропустив звірку, падає, а не деплоїть без охорони.
   > ⚠️ Прапорець **не можна** виставляти в `deploy-env.sh`: той сорситься `deploy-utils.sh` **до
   > будь-якої збірки й до будь-якої звірки**, тож прапорець був би вже виставлений на момент
   > перевірки, `prune_and_build` пройшов би беззастережно — і гейт було б знищено рівно тим кодом,
   > що мав його створити. Єдине коректне місце — тіло `assert_env_matches_account` після обох
   > перевірок.
3. **Статичний тест:** grep-тест, який стверджує, що **кожен** `deploy-*.sh` на диску викликає
   `assert_env_matches_account`. Новий скрипт не зможе тихо приєднатися до непокритих.

```bash
# DEPLOY_ENV = намір (від раннера)   $1 = правда акаунта (з SSM)   $2 = ім'я параметра для помилки
assert_env_matches_account() {
    local account_stage="$1" param_name="${2:-<ssm environment parameter>}"
    [ -n "$account_stage" ] || { echo "FATAL: could not read ${param_name}"; exit 1; }
    [ "$account_stage" = "${DEPLOY_ENV:?}" ] || {
        echo "FATAL: intent '${DEPLOY_ENV}' != account '${account_stage}' (check AWS_PROFILE)"
        exit 1
    }
    DEPLOY_ENV_ASSERTED=1
}
```
Ім'я параметра передається аргументом — інакше у FATAL-повідомленні друкувався б літерал
`/{project}/environment`, тобто плейсхолдер в очі користувачу.
Порожнє/нечитабельне значення → **відмова** (непровіжений акаунт — рівно той випадок, заради якого це
існує).

> ⚠️ **«Першим рядком» — не читати буквально: визначення і виклик у різних місцях.**
> Кожен скрипт читає `/{project}/environment` на **власному** рядку 13/14/19 — тобто **після**
> сорсингу. Отже:
> - **визначається** функція в `deploy-env.sh`, який сорситься першим (через `deploy-utils.sh`);
> - **викликається** — у кожному `deploy-*.sh` одразу **після** його власного SSM-read.
>
> Це саме та пастка з порядком, яка вбила розміщення в обгортках. Записано явно, щоб на рев'ю вона не
> відтворилася втретє.

**Це слідує наявній конвенції lib, а не бореться з нею:** `deploy-utils.sh:60` прямо каже, що
*«SSM /projectName/environment read stays the source of truth) and passes it in»* — lib свідомо **не**
читає параметр, його читають і передають виклики. Варта, що приймає стадію як `$1`, лягає точно в цю
конвенцію. Побічний ефект, який робить §9.3 коректним: `deploy-env.sh` лишається **project-agnostic**,
а отже побайтово однаковим в обох репо.

Ще одне з `deploy-utils.sh:6`: там `set -e`, і його успадковує кожен скрипт, що сорсить lib — тобто
hulyo-шний `deploy-media.sh` є **єдиним** скриптом узагалі без `set -e`.

*Claim Critic'а, що це заблокує travelist, — спростовано (і він це визнав): `/travelist/environment`
читається у `deploy-docs-fe.sh:19` і 14 сусідах, `/hulyo/environment` — у 13.*

### 9.3 Дистрибуція без publish-гейта

`deploy-env.sh` **комітиться в обидва репо руками** — так само, як уже живе `deploy-utils.sh`
(побайтово ідентичний, `sha256 def94656f8da64c0…`). Файл не містить назви проєкту (розділення
`{project}` живе в кожному `deploy-*.sh`, не в спільній lib), тож може лишатися побайтово однаковим.

**Цілісність — на merge-шляху, не в шляху деплою** *(Critic #3 щодо v3):* CI-джоб у code-quality
**порівнює** (не «регенерує» — у v4 ніщо нічого не генерує) файл з **еталонною копією**, і падає на
PR, де його відредаговано руками або він розійшовся з еталоном.

**Чесне формулювання, без перебільшення** *(Critic #2 leftover)*: два репо не бачать дерев одне
одного, тож «розійшовся між репо» з середини одного репо непіддається перевірці. Це неминуче
зводиться до «збігається з еталонною копією» — а отже **канонічний `deploy-env.sh` таки живе в CLI**,
хоч і суто дорадчо. Це відрізняє його від `deploy-utils.sh`, у якого еталона немає ніде.
Залишковий наслідок: зміна контракту = publish еталона → PR-джоби обох репо червоніють → кожне репо
оновлює файл.

> Тобто точно: **шлях деплою не має залежності від infra-kit узагалі**; зміна контракту має
> publish-крок у **review**-шляху. Принцип 6 тримається — але формулювання «виконано абсолютно» було
> завеликим, і я його знімаю. Застарілий CLI ламає щонайбільше PR-джоб, ніколи не деплой.

Що робить сам `deploy-utils.sh` — дешево й без залежностей: перевіряє, що файл **існує**, і
**жорстко падає до будь-якої збірки**, якщо ні. Ніколи warn-and-continue — це був би §2 наново.

### 9.4 Дві точкові правки (корисні й CI)

- `deploy-utils.sh:98` — `rm -rf "${DEPLOY_OUT_DIR:-./out}"`. Локально дефолт — **temp-дір**, і
  відмова, якщо `./out` трекнутий і брудний *(Critic suggested #1)*. У travelist `out/` трекнутий.
- `deploy-utils.sh:82-85` — локально `pnpm dlx` / локальні devDeps замість `pnpm add -g`; `-g`
  лишається для CI *(Critic suggested #2)*. Інакше глобальний тулчейн отруюється на **першому** ж запуску.
- Заголовок кожного `deploy-*.sh` документує дворядкову преамбулу — `DEPLOY_ENV:?` змінює те, що
  означає «запускається самостійно» *(Critic suggested #3)*.

**Exit gate Phase 0** *(Critic #8 — послідовність виправлено):*
1. спершу окремий commit, що лише **друкує** три змінні в CI;
2. зняти по одному baseline-рану на репо;
3. **тоді** заводити індирекцію і дифати проти baseline.
(Інакше «дифати проти попереднього рану» неможливе — попередній ран нічого не друкував.)

**Phase 0 цінна сама по собі: якщо більше нічого не поїде, живий баг у обох репо полагоджений, і
звірка env↔акаунт працює в CI теж.**

## 10. Phase 1 — `infra-kit deploy`

### 10.0 Потік вибору — дзеркалить CI *(додано на запит: «спочатку all чи selected, потім сервіси»)*

CI має **два** воркфлоу: `deploy-all.yml` і `deploy-selected-services.yml` (16 boolean-інпутів).
CLI дзеркалить це трикроково, у тому ж порядку, що й CI (там `environment` — перший інпут):

```
1. Середовище   → пікер (readWorkflowEnvOptions, лише для списку)
2. Режим        → «Deploy all» | «Deploy selected»
3. Сервіси      → лише для «selected»: МУЛЬТИ-вибір, ВІДФІЛЬТРОВАНИЙ під обране середовище
```
Середовище першим саме для того, щоб крок 3 міг відфільтрувати непридатні сервіси, а не показати їх і
дати обрати те, що все одно скіпнеться.

Неінтерактивні відповідники: `--all` ↔ `deploy-all.yml`, `--service a --service b` ↔
`deploy-selected-services.yml`. `--all` і `--service` взаємовиключні.

### 10.0.1 Придатність сервісу до середовища — **я цього спершу не перевірив**

`--all` **не сміє** означати «усе, що дав глоб». У CI є per-service `if:`-умови, і вони різні:

| Сервіс | hulyo | travelist |
|---|---|---|
| `docs-fe` | `dev arthur eliran renana roman oriana` (**не** stage/prod) | те саме |
| `mobile` | **тільки** `dev`, `prod` | те саме |
| `media` | усі середовища | **тільки `prod`** |
| решта | усі | усі |

Тобто `--all --env stage` за наївним глобом задеплоїв би `docs-fe` і `mobile`, яких CI **не** деплоїть.
`--all` визначається як **«те саме, що зробив би `deploy-all.yml` для ЦЬОГО середовища»**.

**Але джерело правди — не YAML, а скрипт.** `deploy-utils.sh:62-74` уже має `skip_unless_env_enabled`,
і його докстрінг (`:57-61`) прямо каже: *«Defense-in-depth alongside the workflow-level env gate:
protects **manual runs** and any other pipeline that wires the script in»* — тобто **кодова база вже
передбачила локальний запуск**. Конвенція є; її треба лише дотягнути.

Поточне покриття guard'ом:

| Репо | Скрипт | обмеження в CI | `skip_unless_env_enabled` |
|---|---|---|---|
| hulyo | `deploy-mobile.sh:17` | dev, prod | ✅ збігається |
| hulyo | `deploy-docs-fe.sh:22` | 6 env | ✅ збігається |
| travelist | `deploy-docs-fe.sh:22` | 6 env | ✅ збігається |
| travelist | `deploy-mobile.sh` | dev, prod | **❌ ВІДСУТНІЙ** |
| travelist | `deploy-media.sh` | **prod only** | **❌ ВІДСУТНІЙ** |

> 🔴 **Два живих баги в travelist, незалежні від CLI.** Локальний (або будь-який не-гейтований) запуск
> `deploy-mobile.sh` задеплоїть mobile у `arthur`/`renana`/`stage`, а `deploy-media.sh` — media у
> будь-яке середовище, хоча CI дозволяє лише `prod`. У hulyo цей захист є; у travelist його не дописали.
> **Робота Phase 0:** додати обидва виклики — рівно по одному рядку, за наявним зразком.

Після цього CLI **не потребує власної копії правил**: він фільтрує пікер з тих самих
`skip_unless_env_enabled`-рядків (парсинг третього аргументу), а скрипт лишається енфорсером. Жодного
четвертого місця для дрейфу — рівно те, чого вимагає §6.

### 10.0.2 Terraform — **чому його немає, і що це означає точно** *(додано на запит)*

Обидва воркфлоу мають інпут `skip_terraform_deploy` з дефолтом **`false`**, тобто CI за замовчуванням
**запускає terraform ПЕРЕД деплоєм** (hulyo: `terraform-apply-initUser` + `terraform-apply-infrastructure`;
travelist: тільки `infrastructure`), і кожен деплой-джоб чекає на `success` або `skipped`.

Отже точне формулювання, яке мусить бути в `--help`, а не мовчазне припущення:

> **`infra-kit deploy` = CI `deploy-all` з `skip_terraform_deploy=true`.** Не «деплой усього».

Це не вигаданий режим — він існує в CI і ним користуються. Terraform лишається поза командою, бо це
інший рівень привілеїв (§4: root `TERRAFORM_AWS_*`, `role_arn`, весь акаунт), і `apply -auto-approve`
з брудного дерева переписав би інфру. **Розділення вже існує в CI:** окремий воркфлоу
`deploy-terraform.yml` («04 ⚙️ Deploy terraform») запускає обидва terraform-джоби самостійно.

Практичні наслідки, які треба знати:
1. **Локальний деплой припускає, що інфра вже існує.** Terraform створює SSM-параметри та ресурси,
   які деплой-скрипти читають. Для **свіжого** персонального середовища локальний деплой упаде на
   SSM-читанні — і це **правильно**: звірка §9.2 відмовляє на порожньому значенні, тобто провал
   голосний, а не тихий. Перше підняття середовища лишається за CI.
2. **`--with-terraform` не додаємо.** Команда друкує `terraform: skipped (= CI skip_terraform_deploy=true)`
   і, на спробу, вказує на `deploy-terraform.yml`. Явна відмова замість мовчазного пропуску.

### 10.0.3 Видимість для команди — **нова вимога, бо спільний `dev` увійшов в обсяг**

Поки обсягом були лише персональні середовища, це не мало значення. Зі спільним `dev` — має.

**Кожен CI-деплой видно в Slack:** успіх через `_notify-success-jobs.yml` (повідомлення називає
`github.actor` і середовище), провал — через `if: failure()` у кожному деплой-джобі
(`_deploy-serverless-jobs.yml:61-68`). Команда бачить, хто і куди задеплоїв.

> **Локальний деплой у спільний `dev` не лишає жодного сліду**: ні workflow-рану, ні Slack, нічого.
> Хтось ламає `dev` о 19:00 з ноутбука — і ніхто не знає ні що змінилося, ні хто це був.
> Це **регресія спостережуваності**, якої не було в CI-моделі, і вона з'явилася рівно тоді, коли
> спільний `dev` став таргетом.

Варіанти:
- **(a) прийняти** — тільки локальний run record. Дешево, але команда сліпа.
- **(b) оголошувати спільні env** ← рекомендовано. `SLACK_TOKEN`/`SLACK_CHANNEL` — це секрети GitHub,
  локально недоступні; **але Doppler локально є** (`infra-kit env-load`, §5). Покласти вебхук у Doppler
  і постити **тільки для спільних середовищ** — персональні лишаються тихими. Обсяг малий і
  замкнений: одна нотифікація, один секрет, нуль впливу на шлях деплою.

Формат повідомлення дзеркалить CI, з явною позначкою походження: хто, яке середовище, які сервіси,
SHA, чи було дерево брудним, і `(local)` — щоб у каналі локальний деплой не читався як CI-шний.

> ⚠️ Побічно знайдено: `_notify-success-jobs.yml` вживає `${{ inputs.environment }}`, але його
> `on: workflow_call:` **не оголошує жодних inputs** — тобто змінна порожня і повідомлення про успіх
> зараз каже «to ** environment» без назви середовища. Косметично, але це той самий клас, що й решта
> §6; у follow-ups.

```
release deploy-all      --from <ci|local> [--env <name>] [--yes]
release deploy-selected --from <ci|local> [--env <name>] [--services <name>...] [--yes]
  --from ci:    [--version <v>] [--skip-terraform]
  --from local: [--dry-run] [--print-env]
```
House rule: нові команди йдуть плоско (див. `commandPath` у `program.ts`). MCP-твін —
`defineMcpTool` з `requiresHumanConfirm: true` (двофазний гейт), `mcpExposed: true`.

**Сервіси** — глоб `devops/scripts/deploy-*.sh`; точніший за список у воркфлоу **в обидва боки** (§6).
*(Critic suggested #7: unit-асерт про виключення `e2e-*.sh` вакуумний — глоб їх і так не бере;
асертити треба проти `devops/scripts/invoke-groups.mjs`.)*

**Середовища** — `readWorkflowEnvOptions('deploy-all.yml')` **тільки для пікера**; її докблок
(`workflow-envs.ts:19-22`) прямо забороняє вето проти неї. Явний `--env` завжди перемагає.

### Виконання, відкат, гігієна

- `sh ./devops/scripts/deploy-<service>.sh` з `DEPLOY_ENV`/`DEPLOY_BRANCH`/`DEPLOY_SHA`. **CLI не
  переписує контракт — лише подає входи**, як CI. Кілька сервісів — послідовно.
- **Відкату немає, і його немає й у CI** *(Critic #3)*. Half-failed (serverless проїхав, інвалідація
  ні) = стейл-FE проти нового BE. Пишемо прямо; run record фіксує SHA + результат по кожному сервісу;
  при частковій невдачі друкується **точна команда редеплою попереднього SHA** — єдиний шлях назад.
- **`--dry-run` валідує preflight і розв'язаний контракт — і НІЧОГО про те, чи деплой удався б**
  *(Critic #5)*. Так підписано і в аутпуті, і в `--help`. Не продавати як безпечну репетицію.
- **Секрети** *(Critic #6)*: `--print-env` друкує **лише три ключі контракту**, ніколи повний child
  env (там `AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`). Run record: env, сервіси, SHA, account **id**,
  пропущені перевірки — **без креденшелів**, файл `0600`.
- **Супервізія** — `superviseChild`/`killDescendantGroupsNow` (`src/dev/managed-child.ts`), імпорт на
  місці. ⚠️ Перед імпортом у не-dev команду переконатись, що модуль не має top-level сайд-ефектів
  *(Critic suggested #6)*. Переїзд у `src/lib/` **свідомо відкладено**, не вирішено.
- **Конфіг — жодного.** `infraKitConfigObject` — `.strict()`; нова секція вимагала б релізу перед
  адопшеном. Не потрібна: усе виводиться або читається з акаунта.

**Exit gate Phase 1** *(Critic #7)*: заміряти baseline CI для односервісного `docs-fe`→`arthur`
(від `gh workflow run` до завершення), ціль — локально **≤ 50%** цього часу. Не досягли → зупиняємось
на Phase 0, і це **прийнятний результат**.

## 13. Pre-mortem

**1. «Рознесли спільний `dev` з брудного дерева.»** ⬆️ **Ймовірність зросла — `dev` тепер в обсязі.**
Скіп тільки поіменний; перевірка 7 гейтиться окремо; усі скіпи друкуються й логуються. **І головне:
для спільного `dev` чисте дерево (5) — НЕ-skippable**, тобто сценарій закритий механічно, а не
дисципліною. Оголошення (8) робить наслідок видимим одразу, а не за пів дня.
**2. «Phase 0 зламала CI.»** Поведінка зберігається за побудовою (ті самі три змінні). Exit gate —
трикрокова послідовність із блоку **«Exit gate Phase 0»** (після §9.4), бо інакше диф неможливий.
**3. «Локальний деплой у `dev` розійшовся з CI-деплоєм у `dev`, і ніхто не помітив.»**
🔄 **Замінює попередній сценарій «ніхто не користується»**, який спирався на те, що `dev` лишиться за
CI — це більше не так. Тепер два раннери пишуть в одне спільне середовище. Мітигація — рівно те, заради
чого існує Phase 0: **контракт збірки один** (`deploy-env.sh`), тож локальний і CI-артефакт для того
самого SHA ідентичні за побудовою. Плюс перевірка 3 не дає їм їхати одночасно, а оголошення (8) робить
обидва джерела видимими в одному каналі.
*(Старий сценарій «ніхто не користується» знято: він мав мітигацією «для `dev` CI за замовчуванням
правильний», а користувач явно включив `dev` в обсяг. Лишати його означало б носити мітигацію, яка
суперечить рішенню.)*

## 14. Тестування

**Unit** — дискаверинг сервісів (асерт проти `invoke-groups.mjs`, не проти `e2e-*.sh`); матриця

проходить (щоб виправлення не зробило перевірку універсальною); `buildDeployEnv` штампує `-dirty`,
коли дерево брудне, лишаючи `DEPLOY_SHA` сирим.
**Bash (Phase 0)** — ambient `VITE_*` зчищено; відсутній `DEPLOY_ENV` → ненульовий вихід **до збірки**;
фолбеки з git; відсутній `deploy-env.sh` → відмова; `assert_env_matches_account` падає на порожньому
та на розбіжному значенні. *(Харнес уже є: `invoke-lambda.test.mjs` поруч.)*

**Статичний тест покриття** *(нове, обов'язкове — це те, що не дало б §9.2 знову протекти)*: перелічити
`devops/scripts/deploy-*.sh` і ствердити, що **кожен** викликає `assert_env_matches_account`. Тест
падає на нових скриптах, які тихо приєдналися б до непокритих. Другий асерт — прапорець
`DEPLOY_ENV_ASSERTED` вимагається `prune_and_build` і sync-хелперами, тобто пропуск звірки = падіння,
а не беззахисний деплой. **Baseline на сьогодні: 12/15 hulyo і 13/15 travelist — тест має бути червоним
до правок і зеленим після.**
**Strip доживає до збірки** *(Critic suggested #5)* — асертити не кінець `deploy-env.sh`, а момент
збірки: пізній ре-експорт звів би все нанівець, а `--env-mode=loose` його запече.
**Integration** (моки `aws`/`gh`/`git` у PATH; мокати через дефолтний імпорт `fs`) — неспівпадіння ⇒
відмова з **нулем** спавнів; `--dry-run` нічого не спавнить і не пише; активний CI-ран ⇒ відмова;
послідовність і зупинка на першій помилці; SIGINT вбиває групу; exit-код виживає `pnpm exec`
(гейтити `; echo EXIT=$?`).
**Потік вибору та придатність** *(§10.0 / §10.0.1)* — `--all --env stage` **не** включає `docs-fe` і
`mobile`; `--all --env dev` у travelist **не** включає `media` (він prod-only); явний
`--service mobile --env arthur` відмовляє з поясненням, а не тихо скіпається всередині скрипта;
пікер сервісів для обраного середовища показує рівно те, що задеплоїв би CI. Джерело правил —
розпарсені рядки `skip_unless_env_enabled`, тож окремий тест звіряє їх із `if:`-умовами у воркфлоу і
падає на розходженні (сьогодні розходження реальне: travelist `mobile`/`media` без guard'а).
**Terraform** *(§10.0.2)* — команда друкує `terraform: skipped (= CI skip_terraform_deploy=true)`;
`--with-terraform` відмовляє з посиланням на `deploy-terraform.yml`; на середовищі без SSM-параметра
падає **голосно** на звірці, а не деплоїть у порожнечу.
**Non-TTY** — мусить **відмовити**, не тихо пропустити підтвердження (`script -q /dev/null`).
**E2E** — реальний `docs-fe` → `arthur`; асерт **не** по мініфікованому бандлу, а: витягнути
задеплоєну сторінку і перевірити **розв'язаний домен** за логікою `constants/index.ts:9-28`
*(Critic suggested #4)*. Єдиний тест, що доводить полагодження §2 — працює вже після Phase 0.
⚠️ Мішень валідна **лише після** правки §9.2: сьогодні `deploy-docs-fe.sh` не викликає жодної з
обгорток у ОБОХ репо, тож до правки цей E2E пройшов би зелено, нічого не довівши про звірку
env↔акаунт. Після правки він покриває і контракт, і звірку — і саме тому лишається мішенню.
**Observability** — run record на успіх і на провал; підсумок називає кожен скіп і крок зупинки.

## 15. Відкриті питання

1. ~~**Чи є AWS SSO / Identity Center?**~~ **ЗАКРИТО (рішення користувача):** креденшели вже присутні
   в shell-сесії терміналу; персональні середовища — теж нормальний таргет. Окремої роботи з
   роздачею креденшелів не потрібно.
   > **Але це підсилює, а не послаблює звірку §9.2.** Ambient-креденшели в шелі — це рівно той
   > механізм, яким деплоять не туди: середовище береться з того, який профіль зараз експортовано, а
   > не з наміру. Тому перевірка «намір == акаунт» лишається **не-skippable**, і саме вона є ціною
   > за зручність «креденшели вже в сесії». Без неї модель «creds у шелі» небезпечніша за CI.
2. ~~**Тільки персональні env, чи й спільний `dev`?**~~ **ЗАКРИТО (рішення користувача): і `dev`, і
   персональні.** Наслідки рознесені по плану: перевірка 5 (чисте дерево) стає **не-skippable** для
   `dev`; перевірка 3 (конкурентність) з теоретичної стає обов'язковою, бо `dev` — дефолтний таргет
   CI; додано перевірку 8 і §10.0.3 (оголошення, бо локальний деплой у спільний env інакше невидимий);
   pre-mortem 3 **замінено**, бо старий спирався на «`dev` лишається за CI».
   > **Припущення замість блокуючого питання:** `stage` в обсяг **не** входить — ти назвав саме «дев і
   > персональні», а `prod` виключений політикою (`PROTECTED_ENVS`). Якщо `stage` теж потрібен — це
   > правка одного списку, і він автоматично отримує режим спільного середовища (не-skippable чисте
   > дерево + оголошення + обов'язкова конкурентність). Скажи, якщо так.
3. **Phase 2 — цим заходом чи окремим тікетом?** *(єдине, що лишилося відкритим)*

## 16. ADR

- **Рішення:** полагодити контракт деплою в репо (`deploy-env.sh`, комітиться в обидва репо) **разом
  зі звіркою env↔акаунт у bash**, потім додати `infra-kit deploy` як шар preflight + UX. Скрипти
  лишаються виконавцем. **Деплой не залежить від infra-kit; `audit` лише дорадчо ловить розбіжність.**
- **Драйвери:** живий тихий баг; латентність внутрішнього циклу на персональних env; і без того
  максимальний радіус ураження.
- **Альтернативи:** A — не лікує тихий баг. B — **виграв антитезу**, узятий як Phase 0; CLI лишає собі
  тільки preflight + UX. D — правильний кінець, місяці. **Генерація через `init` (v3) — відхилена:**
  додає publish-гейт, а `0.1.131` vs `0.1.127` доводить, що дрейф вона не усуває.
- **Чому так:** лагодить живий баг у перший день без залежності від тулінгу; звірка env↔акаунт
  захищає всі три шляхи, а не найменш використовуваний; CLI бере рівно той обсяг, що витримав критику.
- **Наслідки:** `deploy-env.sh` дублюється в двох репо **свідомо** — як уже дублюється побайтово
  ідентичний `deploy-utils.sh`; дрейф ловиться PR-джобом проти еталона в CLI (дорадчо, поза шляхом
  деплою). Відкату немає й не буде — документовано, з друком команди редеплою.
  **Phase 0 більша, ніж «12 рядків bash»** — справжній обсяг:
  1. `deploy-env.sh` + виклик звірки в усі 30 `deploy-*.sh` обох репо;
  2. `hulyo/deploy-media.sh` — сорсити lib, читати env, `set -e` (єдиний скрипт узагалі без `set -e`);
  3. `hulyo/deploy-ai-be.sh` — додати SSM-read (звіряти немає з чим);
  4. **`travelist/deploy-mobile.sh` і `travelist/deploy-media.sh` — додати `skip_unless_env_enabled`**
     (`dev prod` і `prod` відповідно). Це два **живих баги**, незалежних від CLI: сьогодні будь-який
     не-гейтований запуск деплоїть їх у середовища, які CI відмовляється обслуговувати. У hulyo
     аналогічний захист є — travelist його не дописали.
- **Follow-ups:** Phase 2 (заводити незалежно). Фантомні `ai-ui`/`widgets-fe`. Розбіжність дропдаунів
  і Environments. `github.event.inputs.*` усередині `workflow_call` (`_deploy-serverless-jobs.yml:43-45`).
