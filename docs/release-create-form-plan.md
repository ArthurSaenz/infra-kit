# `[BE]` release-create: the wizard's choices as an MCP argument form

**Status:** pending approval · ralplan `--deliberate` · 2026-09-15 · rev 3 · Architect + Critic passes applied · Critic verdict APPROVE (rev 2; three text-only minors folded into rev 3)

Supersedes PR C of `docs/release-create-command-plan.md` (§2.5 `release-form.ts`, §5 row C — designed, never shipped). That design offered an ENUM of computed candidates and kept `releases` required; this one mirrors the wizard's free-text answer and makes `releases` optional. The seam it planned (`ArgumentFormProvider`, the chokepoint state machine) shipped as PRs A/B and is live on five other tools, so nothing below touches `lib/tool-handler` except one pure extraction (§3.2).

## 0. The defect

The CLI asks a human four things; the MCP tool asks nothing and refuses to be asked.

| Surface | Path | What the human gets |
|---|---|---|
| `infra-kit release create` | `apps/infra-kit/cli/src/commands/release-create/release-create.ts:127-221` (`promptForReleasesInteractive`) | "version or name?" (`:146-162`) → `regular\|hotfix` (`:164-180`) → version with a `[<next>]` hint computed from `loadExistingVersions` (`:74-97`, hint at `:75-76`) or a name (`:99-125`) → optional description (`:199-207`) → "Add another?" (`:211-217`) |
| `release-create` MCP tool | same file, `releaseCreateMcpTool` (`:450-531`) | nothing. `releases` is `.array(...).min(1)` and REQUIRED (`:456-500`, `.min(1)` at `:497`); all six `withEscape` sites declare `whenHeadless: 'unreachable'` (`:86`, `:106`, `:161`, `:179`, `:205`, `:216`) — a checked claim that the required field makes them dead under MCP |

Everything an MCP form needs already exists and is live: the `formProvider` seam (`src/types.ts:22-67`, `:82-93`), the chokepoint's form/gate state machine (`src/lib/tool-handler/tool-handler.ts:132-163`), the total form helpers (`src/lib/tool-handler/argument-form.ts`), and five providers — `env-load` (`src/lib/env-load-form/env-load-form.ts`, 5fddcc1) and the four deploy tools (`src/lib/deploy-form/deploy-form.ts`, e9ea02d). `argument-form.ts:33-41` even sizes `FORM_DEADLINE_MS` around "the release provider runs `git ls-remote` and a Jira fetch" — a provider that was never registered. The plugin skill already carries a "Precedence, when a form is also involved" paragraph (`plugins/infra-kit/skills/release-create/SKILL.md:114-119`) for a form that does not exist, and tells the agent that an empty `$ARGUMENTS` means "ask the human what to cut" (`:111-112`) — by chat, because the tool cannot.

**User decision (made, not re-litigated):** the MCP path offers the human the SAME choices through an elicitation form, via `formProvider` on `release-create`.

## 1. RALPLAN-DR

### Principles

1. **One classifier, three surfaces.** What the human types in the form is classified by the SAME function the CLI `--release` flag uses and the skill describes (`SKILL.md:106`): semver or literal `next` → `version`, anything else → `name`. Today that rule is the inline branch at `src/lib/version-utils/next-version.ts:185` inside `parseReleaseSpec` (`:155-199`); it becomes an exported `classifyReleaseToken` that `parseReleaseSpec` and the provider's `toArgs` both call. Classification only — name VALIDATION stays where it is, in `resolveReleaseEntries` → `resolveNamedInput` (`:243-277`, `validateName` at `release-id.ts:66-90`), so a bad name reaches `resolveOrExit`'s named remediation (`release-create.ts:50-72`) instead of a discard that names nothing.
2. **A silent `null` is the enemy.** Every failure on the form path degrades to "no form, gate instead" with no error (`argument-form.ts:99-139`, `:153-171`; measured in `docs/reviews/elicit-schema-measurements.md:34-39`). So every provider test asserts `buildArgumentForm(...) !== null` — the form was OFFERED — never that a gate came back (`deploy-form.ts:12-25`, P10 at `deploy-form.test.ts:196-235`). And a discard the HUMAN can trigger must be unreachable by construction where possible (required `type`, §3.3) or land on a refusal that names the rule (principle 1), never on a `{}` gate that says only "failed validation" (`tool-handler.ts:190-191`).
3. **The schema never depends on the network; only the hint does.** `buildRequestedSchema` runs on BOTH rounds (`argument-form.ts:102-139`), and a `null` on round 2 DISCARDS the human's accepted answer (`readAcceptedArgs`, `:187-195` → `formDiscarded`, `tool-handler.ts:344-350`). A free-text field validates without knowing any prior version, so the `[next]` hint is best-effort under its own budget and the schema is always returned.
4. **The merge is a fixed point of the tool's own parse, under the wire's comparator.** The gate mints its token over `toArgs`'s output (`tool-handler.ts:209-210`, `mintConfirmToken` → `canonicalArgs(stripGateKeys(params))`, `src/lib/tool-handler/confirm-token.ts:164-165`, `canonicalArgs` = `JSON.stringify(sortKeysDeep)` `:78-80`), while round 2's arguments arrive AFTER the SDK's `z.object(inputSchema)` parse (`src/mcp/tools/index.ts:46-48`) — which runs the entry `.transform` (`release-create.ts:487-495`) and defaults `type` to `regular` (`:472-476`). If `toArgs` emits anything the parse would reshape, every form-fed round 2 is refused as `mismatch` (`confirm-token.ts:194`). Two rules make it hold — always emit `type`, omit a blank `description` — and R7 checks them with the wire's own comparator.
5. **`'unreachable'` is a claim, and the claim ends here.** Relaxing `releases` to optional makes every `'unreachable'` in `release-create.ts` false; G8 (`src/lib/prompts/__tests__/headless-policy-guards.test.ts:191-209`) reddens the moment it does, by design (`:14-16`). The six sites become `'refuse'` with the reason written out — what e9ea02d did at `src/lib/prompts/env-picker.ts:47-56` and 5fddcc1 at `src/commands/env-load/env-load.ts:290`.

### Decision drivers (top 3)

1. **Parity with the wizard, one round trip.** A human at the `/` menu should get the wizard's answers in one dialog; the MCP protocol has exactly one form per call (`argument-form.ts:22-31`), so "Add another?" cannot be expressed and multi-release stays agent-args-only.
2. **The wire is measured, or pinned.** Only flat primitives and `z.array(z.enum)` survive `elicit()` (`elicit-schema-measurements.md:17-26`); `releases: [{…}]` cannot be a form field as-is (`:22` — nested object throws). The measured table has no bare `z.string()` (the word appears only in the SDK's error text), so the free-text field is pinned by R2's `buildArgumentForm(...) !== null` rather than by the table, and its live rendering is gated by §5.3 step 0.
3. **Blast radius on the wire baseline.** `required: ['releases']` is in `src/mcp/__tests__/fixtures/tools-list-baseline.v1.json` and the w1 differential compares whole objects (`src/mcp/__tests__/mcp-stdio.e2e.test.ts:1346-1363`); the change must be an AUTHORED, named delta with a `w1c-pre-dN` control — never a re-capture (memory: "MCP tool description edits red W1").

### Options

**A — one flat form mirroring one wizard pass; `releases` optional; form only when `releases` is absent (CHOSEN).**
Fields `type: enum(regular|hotfix)` (required), `release: string` (required), `description: string.optional()`. `toArgs` classifies `release` with the shared `classifyReleaseToken` and returns `{ ...params, releases: [entry] }`. The `release` field's `.describe()` carries the `[next]` hint for both types, computed by `loadExistingVersions` + `suggestNextVersion` under an inner budget.
- Pros: exact wizard parity minus the batch loop — the wizard asks `regular|hotfix` explicitly (`:164-180`), so a required select is the faithful mirror; `z.enum` required is the one shape rendered live (V0.3, `docs/reviews/session-env-picker-v0.md:57`); the free-text field is pinned by R2 and gated by a live render (§5.3 step 0); validation is network-free (principle 3); the human's own `next` appears in the gate and the number appears in the hint and the result.
- Cons: the gate's `resolvedArgs` shows `next`, not the resolved number — `toArgs` is synchronous (`types.ts:66`), and `next` is resolved at execution against whatever `origin` holds then (`next-version.ts:257-258`). This is a BINDING property, not cosmetic: the human approves a symbol. It is also pre-existing — `--release next` and `/infra-kit:release-create next` already mint over `next` today — so A inherits it rather than creating it. A free-TEXT field has not been rendered live in Claude Code yet (V0.1/V0.3 rendered selects only, `session-env-picker-v0.md:43-45`, `:57`). One parity cost of a required `type`: the wizard's select pre-selects `regular` (`default: 'regular'`, `:173`), and a required wire enum with no `.default()` cannot — the human picks explicitly every time. The hint costs up to `HINT_BUDGET_MS` of latency before the dialog on round 1 and before the gate on round 2 (§7).

**B — `version` as an ENUM of concrete candidates (`1.64.0`, `1.63.3`, `next`) plus a free-text `custom`/`name` field.** This is PR C's shape (`release-create-command-plan.md:774-784`).
- Pros: the gate can show an exact number; enum selects are the one shape rendered live.
- Cons: two fields must agree (`version` vs `custom`) and the wire cannot enforce the dependency; the enum can be EMPTY (no prior versions) and `z.enum([])` throws inside `elicit()` (`elicit-schema-measurements.md:23`) so it must return `null` with a log line — i.e. no form at all exactly when a first release needs one; the schema now DEPENDS on the network, so a slow round 2 discards the human's pick (principle 3, `argument-form.ts:120-128` — "a choice that was legal when the human made it can fail now"); and the skill already tells agents "Do not invent a list of candidate versions for the human. Pass `next`" (`SKILL.md:146-147`).
- **Invalidated** by principle 3 (network-dependent validation) and by the empty-enum hole that makes the feature vanish on a first release. Retained ONLY as the named fallback for the `release` field if §5.3 step 0 finds that Claude Code does not render a text input (pre-mortem 4) — in which case this plan is revised, not shipped, because that fallback violates principle 3.

**C — literal wizard mirror: `kind: enum(version|name)` + `value: string` + `type` + `description`.**
- Pros: closest one-to-one with `:146-162`.
- Cons: two fields that must agree with nothing enforcing it (`kind: name` + `value: 1.2.3` is a contradiction the form accepts and `toArgs` must adjudicate); one more field than the information needs — the token already decides its own kind, which is why `classifyReleaseToken` exists and why the flag and the skill (`SKILL.md:106`) never ask.
- **Invalidated** by principle 1: it needs a second rule for the `kind`/`value` disagreement that the shared classifier does not have.

**D — keep `releases` required; add a separate tool (`release-plan`, ungated, `readOnlyHint`) whose form produces the `releases` array for the agent to pass — and, in its sharper form D′, whose HANDLER resolves `next` to a number once, so `release-create`'s gate signs `1.64.0` rather than the symbol.**
- Pros (D′): the gate binds the number; one `loadExistingVersions` instead of three (`argument-form.ts:102-104`, `:193`, `release-create.ts:388-393`); zero wire change on the gated tool — no D19/D20, no G8 flip, no six-site flip, no `isMcpMode` refusal; the form needs no network, so `HINT_BUDGET_MS` and its three prose branches disappear.
- Cons: the user decision (§0) fixes the form ON `release-create`; the symbol-in-the-gate hazard D′ removes is pre-existing behaviour of `--release next` and `/infra-kit:release-create next`, so A inherits it rather than introduces it; D adds a tool surface — catalog default-deny rows, `title`/`annotations`, a manifest `allowed-tools` entry, its own w1 delta — and a two-call chain in the skill; a NAME release resolves nothing, so the planner is a pass-through for half its inputs. Dialog count is NOT a reason: A is form → gate as well. Nor is `humanOnly` (`manifest.test.mjs:669-679`) — it governs the skill's model-invocation, not which read-only tools exist, and an agent can already raise a form on its own initiative with `env-load {}`.
- **Not chosen** for the user decision and the surface cost. **D′ stays recorded as a possible follow-up** (§7): if the symbol-in-the-gate property ever needs to go, a read-only planner that resolves `next` is the shape that removes it without touching the confirm gate.

**E — titled `oneOf` for `type` ("regular — branches off dev") via `fromJsonSchema`.**
Expressible on the wire (`elicit-schema-measurements.md:100-119`) but `buildRequestedSchema` is typed `z.ZodObject<z.ZodRawShape>` (`types.ts:54`; a `fromJsonSchema` result is not one) and Claude Code's rendering of `title` is unmeasured. **Follow-up**, not this change: the per-option explanation rides in the `type` field's `.describe()`, as the env picker does (`env-load-form.ts:93-105`).

**A′ (sub-option, rejected): also offer the form when `releases` is a single `next` entry** (PR C's predicate, `release-create-command-plan.md:751-752`). Rejected: `/infra-kit:release-create next` is an explicit instruction; a dialog there is a re-ask, and every field it could change is one the human already typed. `isFormable` is "releases absent or empty", full stop — which also means `narrowsArgs`'s array-length rule (`argument-form.ts:237-251`) can never fire on this provider: round 1 has no array to compare.

## 2. Scope

**In:** a `formProvider` on `release-create`; `releases` optional at the schema level; the six headless policies; an explicit MCP refusal when no `releases` arrive and no form could; the `[next]` hint with a bounded, injectable budget; `classifyReleaseToken` and `suggestNextVersion` in `version-utils`; `withDeadline` extracted for reuse; tests (provider, schema, headless guards, catalog set, w1 deltas D19/D20, one stdio e2e lane); `SKILL.md` and `readme.md` prose; a pre-publish live render check of the free-text field.

**Out:** batch ("Add another?") over MCP — the protocol carries one form per call, multi-release stays `releases`-only and the skill says so; resolving `next` to a number inside the gate (`toArgs` is sync by contract; D′ is the recorded follow-up); titled enums (E); any change to `lib/tool-handler`'s state machine, `FORM_DEADLINE_MS`, or the confirm gate; forms on other gated tools; the CLI wizard's behaviour; publishing (follow-up, §7).

## 3. Changes (all under `apps/infra-kit/cli` unless noted)

### 3.1 `src/lib/version-utils/next-version.ts` — `classifyReleaseToken` and `suggestNextVersion`
- Add `export const classifyReleaseToken = (token: string): { version: string } | { name: string }` — the `:185` branch lifted out verbatim: `isNextToken(token) || tryParse(token) !== null` → `{ version: token }` (the token AS TYPED — `v1.63.3` stays `v1.63.3`; `resolveReleaseEntries` normalises downstream, `:262-276`, and `tryParse` already strips a `release/` prefix, `:18-20`, `:183-184`), else `{ name: token }` (unvalidated, as today). `parseReleaseSpec` calls it in place of the inline branch, so the flag's behaviour is byte-identical. Export from `src/lib/version-utils/index.ts`.
- Add `export const suggestNextVersion = (known: SemVer[], type: ReleaseType): string | null` — the body of `trySuggestNext` (`release-create.ts:40-48`): `computeNextVersion` (`:76-96`), `NoPriorVersionsError` (`:62-67`) → `null`, anything else rethrown. `release-create.ts:40-48` deleted; `promptForVersionInput` (`:75`) calls `suggestNextVersion`. `release-create-prompts.test.ts` is unaffected (it mocks `@inquirer/input`, not the suggestion).
- Why the helpers live here and NOT as exports of `release-create.ts`: `release-create.ts` will import the provider module to register it, and `createReleaseFormProvider()` is CALLED inside the `defineMcpTool({...})` literal at module scope (`:450`). The new test file is the regression detector for that edit. (`NoPriorVersionsError` is thrown by this module, so its null-returning sibling belongs here anyway.)

### 3.2 `src/lib/deadline/deadline.ts` — `withDeadline` extracted
- Move `withDeadline` (`argument-form.ts:72-96`) verbatim into `src/lib/deadline/deadline.ts` (+ `index.ts`); `argument-form.ts` imports it. Behaviour identical; the f6 deadline lanes (`src/lib/tool-handler/__tests__/tool-handler.test.ts:639-667`) pin it from the chokepoint side.
- Why: the provider needs the same "resolve or `null` after `ms`" for its hint (§3.3), and a THIRD copy would be one too many — `src/lib/mcp-proxy/upstream.ts:224-238` already carries a `withDeadline` with the OPPOSITE contract (rejects on timeout, for a proxy that must fail loudly). The new module's doc comment names that variant so nobody "unifies" the two: this one collapses timeout and rejection into `null` because its callers treat "too slow" and "failed" alike; the proxy's must not.
- Note for §7: `withDeadline` abandons, it does not cancel. `$({ quiet: true })\`git ls-remote …\`` (`load-existing-versions.ts:42`) has no timeout or signal, so a timed-out hint leaves one orphan `git` child per timed-out round on the long-lived server.

### 3.3 `src/lib/release-form/release-form.ts` (new) — `createReleaseFormProvider(options?: { hintBudgetMs?: number }): ArgumentFormProvider`
Mirrors `env-load-form.ts` in shape and `deploy-form.ts` in discipline (fileoverview names the silent-failure property, `:12-25`).

- **`export const HINT_BUDGET_MS = 2_500`**, injectable through `options.hintBudgetMs` (R3 injects 5 ms; AC8 asserts the exported constant). `git ls-remote --heads origin 'release/v*'` over SSH measured 1.65 / 1.80 / 1.88 s on this machine (three runs, this repo, 2026-09-15); `loadExistingVersions` is `Promise.allSettled` over that and the Jira fetch (`src/lib/version-utils/load-existing-versions.ts:68-84`), so its latency is the slower of the two. 2 000 would drop the hint on roughly half of ordinary runs here; 2 500 leaves 500 ms under `FORM_DEADLINE_MS = 3_000` (`argument-form.ts:42`). The chokepoint's timer arms only AFTER `provider.buildRequestedSchema(params)` has been called (`:134-135` — the argument is evaluated first), so the inner timer is armed strictly before the outer one and the headroom covers event-loop latency only. Overrunning the inner budget degrades to "form without the hint" (principle 3); overrunning the outer one is what the inner budget makes unreachable.
- **`isFormable(params)`**: `isRecord(params) && (params.releases === undefined || (Array.isArray(params.releases) && params.releases.length === 0))`. Over the wire `[]` cannot arrive (`.min(1)` rejects it at the SDK parse — executed by the Architect), so the empty-array clause serves unit tests and non-MCP callers only — stated in a comment, as `release-create-command-plan.md:770-772` reasoned.
- **`message`**: `Choose the release to cut. Nothing runs yet: the confirm gate follows, and the agent will show you the resolved arguments to approve.` (Under a gated tool the form feeds the gate — `types.ts:87-89`. The env picker's "picking one LOADS it" sentence is the ungated opposite and must NOT be copied.)
- **`buildRequestedSchema(params)`**, in order:
  1. `hint = await withDeadline(computeHint(), hintBudgetMs)` where `computeHint` = `loadExistingVersions()` → `{ regular: suggestNextVersion(known,'regular'), hotfix: suggestNextVersion(known,'hotfix') }`. That `withDeadline` IS the only collapse to `null`; there is NO provider-level `try/catch` around the whole function — `trySchema` already wraps the provider (`argument-form.ts:129-139`), and a second wrap would only hide a programming error from R2's direct call.
  2. Hint prose, three branches (each a literal the tests match):
     - timed out / rejected → `The "next" hint could not be computed within 2.5 s — "next" still works and is resolved at execution.` + `logger.info({ msg: 'Tool execution form hint unavailable (timeout): release-create' })`.
     - both `null` (no prior versions) → `No prior version is known from origin release/v* branches or Jira, so "next" will be REFUSED — pass an explicit semver.` + `logger.info({ msg: 'Tool execution form hint unavailable (no prior versions): release-create' })`.
     - else → `"next" resolves to <regular> for a regular release or <hotfix> for a hotfix (computed now from origin release/v* branches and Jira fix versions; recomputed at execution).`
  3. Return `z.object({ type, release, description })` — property order is the wizard's order (type before the token; the "version or name?" question is folded into the token itself):
     - `type: z.enum(['regular','hotfix']).describe('Release type. "regular" branches off dev and bumps the minor; "hotfix" branches off main and bumps the patch.')` — REQUIRED, exactly as the wizard asks it (`:164-180`). Not `.optional()`: what a host sends for an UNTOUCHED optional select on Accept has never been observed (V0.1/V0.3 recorded declines only), and if it is `""`, `z.enum` rejects, `acceptedContent` returns `undefined`, `readAcceptedArgs` returns `null` (`argument-form.ts:198-205`) and the WHOLE accepted form — the human's `release` included — is discarded. Required removes that path instead of measuring it, and a required two-option select is the one shape rendered live (V0.3). Not `.default()` either: the command plan's rule (`release-create-command-plan.md:963-974`) is untouched — required ≠ defaulted.
     - `release: z.string().describe('A semver such as "1.64.0", the literal "next", or a kebab-case name such as "checkout-redesign". <hint prose>')` — REQUIRED. There is no round-1 value to keep (the form is offered only when `releases` is absent), so "blank keeps the caller's" is false here and `required` is the honest wire. No `.min(1)`/`.regex()`: neither is in the measured table (`elicit-schema-measurements.md:17-26`); blank is handled by `toArgs`.
     - `description: z.string().optional().describe('Optional. Becomes the Jira fix version description and feeds the PR body. Blank means none.')` — `z.string().optional()` accepts `""`, and `toArgs` folds it, so an untouched field is safe whichever way the host sends it.
  4. Never `null` from this function except through a thrown programming error (which `trySchema` catches on the MCP path and R2 exposes in the unit lane). Unlike deploy/env-load there is no enumeration to be empty — that is the property principle 3 buys.
- **`toArgs(content, params)`** — synchronous, total, MERGES (`types.ts:55-66`):
  1. `token = typeof content.release === 'string' ? content.release.trim() : ''`; `'' → null` — the ONLY `null` this function returns.
  2. `type = content.type === 'hotfix' ? 'hotfix' : 'regular'` — total, and always PRESENT (principle 4: the transform defaults it, so the merged object must already carry it).
  3. `description = typeof content.description === 'string' && content.description.trim() !== '' ? content.description.trim() : undefined` — key OMITTED when undefined (the transform drops it, `:489`, `:493`).
  4. `id = classifyReleaseToken(token)` — `{ version: token }` or `{ name: token }`, never a throw, never a `null`. A name that is not kebab-case, is reserved, or is too long reaches the gate as `{ name: 'Checkout Redesign', type }`, and on round 2 `collectEntries` → `resolveOrExit` (`release-create.ts:50-72`) refuses it with *use a kebab-case name like "checkout-redesign" (lowercase, digits, single hyphens, not a reserved word)* — BEFORE `assertBaseBranchSwitchable` and `confirmReleases` (`:394-419`), so nothing has mutated. That is a refusal that names the rule, where a `toArgs` `null` would be a `{}` gate that names nothing.
  5. Return `{ ...(isRecord(params) ? params : {}), releases: [{ ...id, type, ...(description ? { description } : {}) }] }`.
  - The one `null` (blank token) lands on the `formDiscarded` gate (`tool-handler.ts:346-350`, prose `:190-191`) whose `resolvedArgs` are the round-1 `{}` — confirming THAT is refused by §3.5, so a blank can never execute anything. The skill tells the agent what to do with it (§3.11).
- `isRecord` is module-private, the same three-line guard `env-load-form.ts:24-26` and `deploy-form.ts:48-50` each carry — not imported from either (neither exports it, and a shared `lib/is-record` is not this change's business).
- Imports: `zod`, `src/lib/logger`, `src/lib/deadline`, `src/lib/version-utils` (`classifyReleaseToken`, `loadExistingVersions`, `suggestNextVersion`), `src/types`. No `src/lib/release-id` import (the classifier owns the rule), no MCP SDK import (the catalog bundle guards, `command-catalog.ts:41-44`).

### 3.5 `release-create.ts` `collectEntries` (`:246-264`) — the headless refusal
Before `promptForReleasesInteractive`, when `inputReleases` is absent/empty:
```ts
if (isMcpMode()) {
  throw new OperationError(undefined, {
    operation: 'create release',
    remediation: 'pass "releases" explicitly, or call from a client that can render the argument form (omit "releases" and the human is asked)',
    stderrExcerpt: 'no releases provided and no human to ask',
  })
}
```

## 7. ADR

- **Decision:** register a `formProvider` on `release-create` that mirrors ONE pass of the CLI wizard as a flat form (required `type` enum, required free-text `release` token with a bounded `[next]` hint, optional `description`); make `releases` optional; offer the form only when the agent sent no `releases`; classify the token with the one function the `--release` flag uses; refuse headless with a named remediation; flip the six `'unreachable'` policies to `'refuse'`.
- **Drivers:** wizard parity in one round trip; the measured-or-pinned elicitation wire; a named, controlled baseline delta.
- **Alternatives:** B enum of candidates (network-dependent validation, empty-enum hole, contradicts the skill's "do not invent candidates"; kept only as the fallback if the text field does not render); C `kind`+`value` (a second rule the shared classifier does not have); D/D′ a separate planner tool (loses on the user decision and surface cost, NOT on dialog count or `humanOnly`; D′ recorded as the follow-up that would remove the symbol-in-the-gate property); E titled `oneOf` (follow-up: type mismatch + unmeasured rendering); A′ form over a single `next` (a re-ask of an explicit instruction).
- **Why chosen:** the schema validates without the network, so the human's answer is never discarded by a slow round 2; the two live-rendered shapes are the selects, and the one unmeasured shape (the text field) is pinned by R2 and gated by a live render before publish; the classification is the one function the flag already runs.
