## 1. Summary

Two user decisions, already made:

**A. Argument form.** Today an MCP call to `release-remove` without `version` is refused by `assertMcpRemoveInput` (`«rr»:177-183`, "the interactive picker needs a TTY"). Instead the tool registers a `formProvider` (`«cli»/src/types.ts:22-70`) exactly as `release-create` does (`release-create.ts:19,456`), and the form enumerates the open release PRs — the same source the CLI picker draws from (`«rr»:886`) — as a single-select `z.enum` whose accepted value becomes `version`. The form FEEDS the confirm gate (`requiresHumanConfirm: true`, `«rr»:991`); the refusal stays as the fallback for a client that cannot render a form.

**B. Jira removal over MCP.** The prior plan's D7 (`docs/release-remove-command-plan.md:627-673`, summarised at `:46-49` and `:301-302`: _"Running over MCP → the Jira step is not attempted at all; `jira: 'manual'`"_) is reversed. The argument for D7 was that an agent "can never reach the one irreversible call" (`:645-649`). With the confirm gate on every MCP call and a human filling the form, a human IS in the loop, so the tool does over MCP what it does on the CLI: `assertIssueCountsUnchanged` then `removeJiraVersion`. `'manual'` disappears from the result. `moveIssuesTo` becomes an MCP input field (the count guard's escape hatch, which must be reachable from where the guard now fires); `skipJira` stays CLI-only on a NEW rationale.

## 2. Principles

1. **The form is a picker, not a wizard.** It mirrors what `pickReleaseBranch(formatBranchPickerItems(...))` shows on the CLI (`«rr»:907`): the same candidates, the same labels, the same descriptions — nothing the CLI picker would not offer. Parity is the test.
2. **A refusal must name an exit that is reachable from where it fires.** The previous plan scoped the count guard away from MCP because its own remediation named a flag MCP refused (`«rr»:258-262`). Once MCP deletes, the guard applies over MCP, and its escape hatch has to exist over MCP too. The same rule is applied to every OTHER refusal text an MCP caller can read: the released/archived guard (`:251`), the TOCTOU re-probe (`:755`), the residue report (`:591`) and the typo guard (`:292`, `` check the spelling against `infra-kit release list` ``) each name a CLI flag or a CLI command today and are forked in D7/D9. **The rule, precisely:** over MCP a CLI flag or command may appear in a refusal ONLY in the "ask a human to run … from a configured shell" hand-off shape — never as an action for the caller. That is the shape `:234-235` already uses, and the existing guard test pins it the same way (`release-remove-mcp-guards.test.ts:344`: `not.toContain('pass --skip-jira')`, while the message still names the CLI command as the human's exit). Three hand-off texts are therefore kept or added deliberately: `:235` (unconfigured Jira), D6 row 3 (`skipJira` refused), and the `:251` fork.
3. **Every provider failure is `null`, and `null` is today's behaviour.** The chokepoint flattens rejection, deadline and `null` alike into "no form, fall to the gate" (`argument-form.ts:14-20`, `:104-114`). The provider never throws, and it bounds its own fetches under the chokepoint's `FORM_DEADLINE_MS` (`argument-form.ts:43`, 3 000 ms) so that a miss is the provider's decision with a log line, not the chokepoint's silence. `withDeadline` abandons, it never cancels (`deadline.ts:13`): a `gh` child that outran the budget keeps running, and again on round 2 — the cost is accepted, as it is for release-create's `ls-remote`. The gate-with-no-version that follows a `null` is refused on confirm, never guessed.
4. **The result never reports a mutation that did not happen, and never omits one that did.** `'manual'` was a promise about a step that did not run; once the step runs, the value goes. `runStep` logs the OUTCOME (`«rr»:533-537`) for the same reason.
5. **Prose that describes the MCP path lives in three places and must agree:** the tool `description`/field descriptions (`«rr»:989-1033`), the plugin skill (`plugins/infra-kit/skills/release-remove/SKILL.md`), and the catalog comments (`command-catalog.ts:291-296`, `:666-668`; `command-catalog.test.ts:283-286`). The manifest test `U18` for procedure skills is PRESENCE-only (`manifest.test.mjs:912-920`: every clause in `PROCEDURE_CLAUSES` must appear; nothing asserts absence), so removing a clause from the list does not fail when the sentence survives. The session-body `U18` already has the absence pattern (`:842-849`: `assert.equal(joined.includes('four most likely'), false)`); D13 adds the same for `release-remove`, and AC-12's grep covers the two code comments the test cannot see.

## 3. Decision drivers (top 3)

- **DD-1 — the confirm gate + the form put a human on every MCP removal.** Round 1 draws the form (`tool-handler.ts:408-425`), Accept merges into the round-1 arguments and lands on a gate whose `confirmToken` is an HMAC over exactly those arguments (`tool-handler.ts:209-235`, `confirm-token.ts`), round 2 verifies and enters the handler. This is the fact that retires D7's "the agent never reaches the irreversible call": the agent still cannot reach it _alone_.
- **DD-2 — the elicitation wire and the chokepoint's deadline constrain the form's shape and cost.** Measured shapes are flat objects of `enum` / `array(enum)` / `string` with field-level `.describe()` only (`deploy-form.ts:90-97`, `docs/reviews/elicit-schema-measurements.md`); `z.enum([])` throws inside `elicit()` and reads as "no form" (`deploy-form.ts:123-130`); the provider is rebuilt on round 2 (`argument-form.ts:81-103`), so anything it fetches is fetched twice per accepted form and must fit 3 s each time. Measured by the Critic on this repo (warm `gh` auth, 3 runs): one `gh pr list --search` takes 662 / 658 / 728 ms, so the two SEQUENTIAL searches in `fetchAllReleasePRs` (`gh-release-prs.ts:76-81`) cost ~1.4 s median with an unbounded tail — under 3 s ordinarily, not by enough to leave the tail to the chokepoint. D4 parallelises the pair and budgets the provider's own fetches.
- **DD-3 — the refusal-with-no-exit shape (prior plan's D-a, `release-remove-command-plan.md:101-105`) must not reappear in the new form.** The prior plan avoided it by not deleting over MCP. This plan avoids it by making the escape hatch an MCP argument.

## 5. Decisions

### D1 — the provider module: `src/lib/release-remove-form/`

New `«cli»/src/lib/release-remove-form/release-remove-form.ts` + `index.ts` exporting `createReleaseRemoveFormProvider(options: { fetchBudgetMs?: number } = {}): ArgumentFormProvider` and `FETCH_BUDGET_MS`. Registered on the tool literal as `formProvider: createReleaseRemoveFormProvider()` next to `requiresHumanConfirm: true` (`«rr»:991`).

Import rule, copied from `release-form.ts:19-22`: the provider imports from `src/lib/**` and `src/integrations/**` only (deploy-form already imports `getReleasePRsWithInfo` from `src/integrations/gh`, `deploy-form.ts:3`), never from `src/commands/**` — `release-remove.ts` registers the provider inside its module-scope `defineMcpTool({...})` literal, so a back-import would evaluate that literal before the provider module's body exists (ESM TDZ). The detector is the provider test's `vi.resetModules(); import('../release-remove-form')` (precedent `release-form.test.ts:272-278`).

### D2 — enumeration source: the open release PRs, as the CLI picker

`getReleasePRsWithInfo()` (`gh-release-prs.ts:155-165`; two `gh pr list` searches, `:78-81`) → `pr.branch` → labels via `releaseBranchLabels` (`release-utils.ts:318-326`, drops non-parsing branches; the same helper `deploy-form.ts:79-88` uses). This is byte-for-byte the CLI picker's source (`«rr»:886-889`) and produces the labels `resolveReleaseBranch` accepts (`release-utils.ts:285-294`), so the merged `version` round-trips through `resolveTargetBranch` (`«rr»:882`) unchanged.

Rejected sources, each with the reason:

- `getCurrentWorktrees('release')` (`git-utils`): a worktree-less release (PR + branches only — a common resume state) would be un-pickable, and a worktree with no PR is `release-create` residue that `version` handles directly. The CLI picker does not consult it either.
- Union of PRs + worktrees + `git ls-remote --heads origin 'release/*'`: three network sources under one 3 s budget, twice per accepted form (DD-2); and it would offer releases the CLI picker never shows, breaking principle 1. The picker's own refusal text already names the exit for partially-torn-down releases: "pass `--version <ref>`" (`«rr»:892-898`) — over MCP that is passing `version`.

Three ways the enumeration can yield nothing, and each gets its OWN log line so a miss on a real repo is attributable from stderr (the e2e stub can never miss, PM-1):

| Outcome                                       | Provider answer | Log line (`logger.info({ msg })`)                                               |
| --------------------------------------------- | --------------- | ------------------------------------------------------------------------------- |
| `gh` answered, zero open release PRs          | `null`          | `Tool execution form options empty (open release PRs): release-remove`          |
| `getReleasePRsWithInfo` rejected              | `null`          | `Tool execution form enumeration failed (gh pr list): release-remove`           |
| the enumeration outran `FETCH_BUDGET_MS` (D4) | `null`          | `Tool execution form enumeration timed out (gh pr list, 2.5 s): release-remove` |

(shape of `deploy-form.ts:123-130`; unlike deploy-form's `orEmpty` (`:70-77`), rejection and emptiness are NOT collapsed, because the human's next step differs — "there is nothing to remove" vs "check `gh auth status`" vs "the network was slow, re-call".) All three land on the gate; confirming a gate with no `version` is refused by `assertMcpRemoveInput` (D6), whose remediation lists these causes and points at the log.

**`fetchAllReleasePRs` runs its two searches in parallel** (`gh-release-prs.ts:76-81`: today `await` dev, then `await` main): `Promise.all` of the two `$` calls, then the same parse/`warnIfTruncated`/dedupe. Order of the merged list is unaffected (`loadSortedReleasePRs` sorts). Its test mocks by `--base` substring (`gh-release-prs.test.ts:62-68`), so it is order-agnostic and stays green. This halves the CLI picker's wait too (`«rr»:886`).

### D3 — the form shape

```ts
z.object({
  version: z
    .enum(labels)
    .describe(
      `The ONE release to tear down. Open release PRs right now: ${rows}. ` +
        'Nothing runs yet: the confirm gate follows, and the agent will show you the resolved arguments to approve. ' +
        'Removal deletes the worktree, closes the PR, deletes both branches AND removes the Jira fix version — the last is irreversible.',
    ),
})
```

- **Required, not `.optional()`.** Round 1 has no usable `version` by construction (`isFormable` = `isRecord(params) && (params.version === undefined || params.version === '')`), so "blank keeps the caller's" (deploy-form's reason for `.optional()`, `deploy-form.ts:141-146`) has nothing to keep; and release-form records that an untouched optional select on Accept is an unmeasured wire shape (`release-form.ts:103-106`). Required means Accept cannot arrive without a value.
- **`version: ''` is formable**, the env-load reading (`env-load-form.ts:74` treats `config: ''` as absent). A blank string passes `z.string().optional()` at the SDK parse and would otherwise land on a gate that `assertMcpRemoveInput` refuses on confirm (`''` is falsy at `«rr»:177`); offering the picker instead is the better exit, and `toArgs` overwrites the blank. `{ moveIssuesTo: 'x' }` with no `version` is likewise formable and the merge KEEPS `moveIssuesTo` (§4.2 B1 counts row). Both pinned in `f1`/`f8`.
- **`rows`** = one entry per label, `1.2.5 [regular]` / `checkout-redesign [hotfix] — <Jira description>`: type from `detectReleaseType(pr.title)` (`release-utils.ts:249`, the derivation `resolveTargetBranch` uses at `«rr»:900-904`), description from `getJiraDescriptions()` keyed by `formatJiraName(parseBranchName(branch))` — the same keying `formatBranchPickerItems` uses (`release-utils.ts:338-341`; per memory, a branch-keyed lookup renders nothing silently). Rendered in the FIELD prose because the elicitation enum has no per-option labels (`deploy-form.ts:90-97`).
- **`message`**: `'Choose the release to remove. Nothing runs yet: the confirm gate follows, and the agent will show you the resolved arguments to approve.'` (release-form's wording, `release-form.ts:84-86`; the form feeds the gate).
- **`toArgs`**: `{ ...(isRecord(params) ? params : {}), version }` when `content.version` is a string, else `null`. Total; never constructs a fresh object (`types.ts:52-60`). `narrowsArgs` cannot trip: round 1 carries no `version` key (or a blank one, which the merge replaces — substitution is the feature, `argument-form.ts:205`) and no arrays.
- **No `(released)`/`(unreleased)` decoration on the rows.** The Architect noted `getProjectVersions` (which `getJiraDescriptions` already calls, `release-utils.ts:212`) carries `released`/`archived` per version at zero extra network. Not adopted: it exceeds what the CLI picker shows (`formatBranchPickerItems` renders label, description and type only, `release-utils.ts:328-345`) and so contradicts principle 1. Recorded as a follow-up (§11) that would need a P1 amendment, not a quiet addition.

### D4 — budget

`FETCH_BUDGET_MS = 2_500`, applied to EACH of the provider's two fetches independently, in parallel: `Promise.all([withDeadline(enumerate(), budget), withDeadline(getJiraDescriptions(), budget)])` (`deadline.ts:17`, resolves `null` on timeout or rejection; `enumerate()` wraps `getReleasePRsWithInfo` so that rejection and timeout stay distinguishable — D2's table). The provider therefore answers within ~2.5 s plus event-loop latency, inside the chokepoint's 3 000 ms (`argument-form.ts:43`), which arms only after the provider's promise exists (the release-form headroom argument, `release-form.ts:28-33`). A slow `gh` is the provider's `null` with the `timed out` line, never the chokepoint's silent `null`. A timed-out Jira costs only the descriptions: rows render as `1.2.5 [regular]` and the prose appends `Jira descriptions could not be fetched within 2.5 s.` with `logger.info({ msg: 'Tool execution form descriptions unavailable (timeout): release-remove' })`. A unit test pins `FETCH_BUDGET_MS < FORM_DEADLINE_MS` (precedent `release-form.test.ts:136-140`).

Why 2 500 and not lower: the Critic's measurement (DD-2) puts the parallelised enumeration at ~0.7 s median; 2 500 leaves the tail ~3.5× headroom and matches release-form's `HINT_BUDGET_MS`, which was chosen against the same 3 000 ms ceiling. The implementation PR re-measures `getReleasePRsWithInfo` three times on a CONSUMER repo (hulyo or travelist, more PRs than this repo) before the number is final, and records the runs in the constant's comment as `release-form.ts:26-34` does.

Why the descriptions are worth a fetch at all: they are what the CLI picker shows (`formatBranchPickerItems`, `release-utils.ts:328-345`), and for a named release they are the only thing that tells a human `checkout-redesign` from `checkout-redesign-2`. `getJiraDescriptions` already never throws (`release-utils.ts:218-230`).

### D5 — the schema is rebuilt on round 2, and that is correct here too

`trySchema` runs on both rounds (`argument-form.ts:77-79`); nothing is cached (`:81-93`). Drift consequence for this tool: a release whose PR was merged or closed between round 1 and round 2 vanishes from the enum, the accepted content fails validation, and the call lands on the `formDiscarded` gate (`tool-handler.ts:350-355`). That is the right direction: `assertNotMerged` (`«rr»:203-211`) would refuse the same release on confirm anyway. No plan step caches anything across requests.

## 7. Pre-mortem

**PM-1 — the form is never drawn and nobody notices, because every failure reads as a gate.** Two sub-cases. (a) A SHAPE defect: `buildArgumentForm` returns `null` on a thrown `elicit()` (`argument-form.ts:137-145`) — `z.enum([])`, a nested object, an async refine — and the handler gates as if the client had no elicitation. Mitigation: `f2` asserts `buildArgumentForm(provider, {}, 3000) !== null` on the wire shape (the deploy-form discipline, `deploy-form.ts:19-25`); `f4` asserts the EMPTY enumeration returns `null` with its log line; `e-rr1` drives the real bundle with the stubbed `gh` (`env-picker-fixture.ts:56-75`, which answers `pr list --base dev` with `release/v1.2.5`) and asserts the spy saw one `elicitation/create`. (b) An ENVIRONMENTAL miss the fixture cannot reproduce: on a real repo the two `gh` searches take ~1.4 s sequential median with an unbounded tail (DD-2), so a slow network drops the form at the chokepoint's 3 s with no line that says why, and the human then reads a refusal that blames the client. Mitigations baked in: the searches run in parallel (D2, step 0); the provider bounds the enumeration itself at `FETCH_BUDGET_MS` and writes one of THREE distinct lines — options empty / enumeration failed / enumeration timed out (D2's table, pinned by `f4`, `f5`, `f11`); the D6 refusal lists those causes and points at the log instead of asserting the client cannot render forms; and the implementation PR re-measures on a consumer repo before the budget is final (D4).

**PM-2 — round 2 executes a removal the human did not confirm, because `toArgs` emitted a shape the tool's transform re-normalises.** The gate signs canonical arguments; if the merged object and what round 2 parses differ, the verdict is `mismatch` — fails safe, but silently useless. Mitigation: `f7` asserts every `toArgs` output is a fixed point of `z.object(releaseRemoveMcpTool.inputSchema).parse(...)` (precedent `release-form.test.ts:234`); `e-rr1` asserts round 2 logs `Tool execution failed: release-remove` and NOT `Tool execution refused (` — the same load-bearing pair `e-r1` uses (`mcp-stdio.e2e.test.ts:1235-1240`).

**PM-3 — an agent reassigns issues on its own initiative.** With `moveIssuesTo` an MCP input, an agent could answer the count refusal by inventing a target. Mitigations: (a) `resolveMoveTarget` refuses a name Jira does not know, before any mutation (`«rr»:363-373`); (b) an existing-but-wrong target still needs the human's confirm, and `resolvedArgs` shows it (`confirm-token` binds it); (c) the skill's §5 carries the literal sentence "Do not pass `moveIssuesTo` on your own initiative — only a name the human gave you.", and U18's PRESENCE list pins that sentence, not a bare token; (d) the field description says "pass it only after a refusal reported the counts, or when the human named the target". Residual risk accepted and stated: this is the CLI's `--move-issues-to --yes` shape, now behind one more human step than the CLI has; and, per §4.2 B1's counts row, a round-1 `{ moveIssuesTo }` plus the form reaches the same shape — not new, pinned by `f1`/`f8`. Out of scope, recorded (Architect #10): `resolveMoveTarget` checks existence only, so a RELEASED target can receive the issues — pre-existing on the CLI; the `JiraVersion` carries the flags if a later change wants the check.

**PM-4 — a stale `'manual'` / "never removed" sentence survives somewhere prose-only.** Unit and e2e tests cannot see a Markdown sentence or a code comment. Mitigations: `RETIRED_CLAUSES` asserted ABSENT in U18 (D13) — the presence list alone would not fail if a retired sentence survived; and AC-12's grep, whose terms cover the retired vocabulary (`manual`, `left in place`, `never attempted`, `never removed`, `never touches`, `do not block`, `no tool field`, `no picker`) and whose paths include `src/lib/command-catalog` for the two comments (`command-catalog.ts:666-668`, `command-catalog.test.ts:284-286`) outside every test's reach.

## 11. ADR

- **Decision.** Register a `formProvider` on `release-remove` that offers the open release PRs as a required single-select `version` enum with `[type]` and Jira-description rows in the field prose, each fetch bounded at `FETCH_BUDGET_MS` with a distinct log line per miss, the two `gh` searches parallelised; make `version` optional in the input schema and keep `assertMcpRemoveInput`'s refusal as the no-form fallback, worded by cause. Over MCP, run the Jira step — TOCTOU re-probe then `removeJiraVersion` — and drop `'manual'` from the result. Expose `moveIssuesTo` as an MCP input (not on the form); keep `skipJira` CLI-only; apply the count guard on every path, and fork every MCP-readable refusal/residue text that named a CLI flag or command as a caller action (`:251`, `:292`, `:591`, `:755`, `:269-275`).
- **Drivers.** DD-1 the gate + form put a human on every MCP removal; DD-2 the measured elicitation wire and the 3 s rebuild-per-round budget; DD-3 no refusal without a reachable exit.
- **Alternatives considered.** A2 multi-select (contradicts the command's single-target contract, D6 of the prior plan; deferred); A3 free text (the candidates are enumerable; rejected). B2 expose `skipJira` too (an orphaned live fix version with `jiraVersion: null` in the result; rejected); B3 expose neither (coherent, human-only exit like D2c, but refuses the ordinary case with an exit outside the tool; recorded as fallback); B4 `moveIssuesTo` on the form (blind reassignment before counts are known; deferred). Enumerating worktrees or `ls-remote` instead of/in addition to PRs (breaks picker parity, triples the network under one budget; rejected). Keeping `'manual'` in the enum for compatibility (nothing produces it, no fixture pins it; rejected). Caching the round-1 schema for round 2 (`argument-form.ts:81-103` explains why not; not considered further).
- **Why chosen.** The form mirrors the one picker the CLI already shows, from the one source it reads, so a human over MCP picks from exactly the list a human on a TTY would; the irreversible step is now reachable only through a human-confirmed gate whose token binds the arguments; and the guard that protects that step names an exit that exists on the same path.
- **Consequences.** `tools/list` changes for `release-remove` (optional `version`, new `moveIssuesTo`, new prose, `jira` enum shrinks) — all `AUTHORED` in the e2e differential; one more key in the golden snapshot; two Jira/`gh` fetches per accepted form (rebuild) — tolerated as in release-create; the D2c/D3 refusals and the merged-PR guard are unchanged; a partially-torn-down release (closed PR) is not in the picker — `version` is the exit, as on the CLI; U18 gains an absence loop so the retired sentences cannot survive a merge; the prior plan's D7 is annotated, not rewritten. **Version-skew window, accepted:** the plugin skill (marketplace) and the global CLI (`pnpm add -g infra-kit`, memory: consumers run the global infra-kit) are not installed in lockstep on a consumer machine. Until both are updated, an OLD server answers `jira: "manual"` to a NEW skill that expects `"removed"` (the agent relays a value the skill does not name — harmless, the version is still there with its URL), and a NEW server answers `"removed"` to an OLD skill that promises "never removed over MCP" (the dangerous direction: the skill's §2 would not have told the human before call 2). Mitigation is procedural, not code: the same release bumps `plugin.json` and the CLI, the `[DO] release` step runs `pnpm add -g infra-kit@<exact>` on the user's machines before the marketplace is refreshed, and the new tool description says "REMOVES ITS JIRA FIX VERSION" in the text every host shows the agent regardless of skill version — that description is the one surface immune to skew. `withDeadline` abandons rather than cancels: a timed-out `gh` child keeps running to completion, twice per accepted form at worst — accepted, as for release-create's `ls-remote` (`release-create-form-plan.md` §7 Consequences).
- **Follow-ups.** A2 multi-select (`versions[]`, a per-release residue report, one gate for N — re-opens D6 of the command plan); B4 `moveIssuesTo` on the form as an enum of the project's other unreleased versions, once a two-select form has a measured render and blind reassignment has a decision; `(released)`/`(archived)` decoration on the picker rows from the `getProjectVersions` data already fetched — needs a principle-1 amendment first, since the CLI picker does not show it; a released-target check in `resolveMoveTarget` (Architect #10, pre-existing on the CLI); a `title` on the enum rows if the wire ever grows per-option labels; a timeout/signal on the `gh` children so a timed-out enumeration does not orphan them; lockstep publish (bump → publish config → re-pin → publish cli) and `plugin.json` alignment in the same release.
